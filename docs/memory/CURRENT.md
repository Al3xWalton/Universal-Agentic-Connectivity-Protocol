The Stage 8a parser handled the typical `<url>; rel="next"` case but glossed over rel case-insensitivity, multiple rels per entry, multi-Link-header concatenation, relative-URI resolution, link parameters beyond rel, and the comma-inside-brackets edge case. Without spec backing, every Conforming Implementation would have to figure these out independently and likely diverge on real providers like GitHub. Path A again — additive, clarifying amendment to §3.4 enumerating seven RFC 8288 conformance rules. Non-breaking per Principle 6 / §7.2; the rules clarify behavior that was implicit but unspecified, and existing implementations that already handled the typical Link shape correctly continue to work. **`api_key_header` covers GitHub's three PAT formats trivially** — `ghp_` (classic), `github_pat_` (fine-grained), `gho_` (OAuth-app-issued) all use the same `Authorization: Bearer <token>` wire shape and UACP doesn't distinguish them. The artifact says "API key in Authorization header"; the runtime injects whatever the secret store resolved. Format-agnostic by design, which is exactly the simplification the brief expected. **`api_key_query` (§2.4.2) implemented alongside** with the §2.4.2 disrecommendation warning emitted on every apply — the spec prescribes the warning surface, the prototype emits via stdlib logging so the dispatcher's audit pipeline can capture it. **Strengthened RFC 8288 parser** in `dispatch/pagination.py` handles: (1) string OR list[str] input (HTTP allows multiple Link headers); (2) comma-separated entry splitting that respects angle brackets and quoted values (so commas inside URIs or quoted titles aren't treated as entry separators); (3) rel case-insensitivity per RFC 8288 §3.3; (4) space-separated multiple rels per entry per §3.3; (5) multiple link parameters per entry (title, type, hreflang) with only `rel` consumed for pagination; (6) quoted vs unquoted parameter values; (7) relative URI resolution per §3.4 against the request URL (with subsequent advances resolving against the most-recent URL, not the artifact base). Non-breaking per Principle 6 / §7.2. **SigV4 implementation written from scratch** using only `hashlib` + `hmac` from stdlib. No `boto3` / `botocore` dependency — UACP's whole point is owning the auth implementation. Streaming-upload UNSIGNED-PAYLOAD is flagged as a Stage 9 consideration; v1 dispatch §4.7 covers streaming responses but not requests, and S3's typical use cases here (GetObject + ListObjectsV2) don't need it. **No new entries to `docs/open-questions.md`** — body-format gap closed in spec; SigV4 implementation matches AWS test vectors; UNSIGNED-PAYLOAD streaming-upload flagged as Stage 9 design but not currently a v1 concern. **Hard rules honored**: did not depend on boto3 or botocore (SigV4 from scratch); did not change Google or Slack code (SigV4 is purely additive in `auth/aws_sigv4.py` replacing the stub); .uacp files validate cleanly through `spec.loader.load()` after the §3.3 format-field amendment; did not push the repo.
